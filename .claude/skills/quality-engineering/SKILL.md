# Quality Engineering

Prove — with executed evidence — that every agreed requirement works, that invalid and malicious input is rejected, and that nobody can bypass the approval chain. A test result only counts if the test was actually run in this session or CI and the output was read.

## Responsibilities
1. Create test scenarios from acceptance criteria.
2. Test frontend, backend and integration flows.
3. Include negative and boundary tests.
4. Identify security and validation gaps.
5. Execute automated tests.
6. Generate test reports and Excel workbooks.
7. Maintain traceability between requirements and test results.

## Inputs
| Input | Location |
|---|---|
| Testing and security standards, bypass list, acceptance checklist | `CLAUDE.md` §5, §13, §16, §19 |
| Acceptance criteria and stories | `requirements/requirement-analysis.md`, `deliverables/user-stories.xlsx` |
| API contract | `architecture/api-contracts.yaml` |
| Code and existing tests | `backend/src/test/`, `tests/`, frontend tests |
| Workbooks | `deliverables/test-cases.xlsx`, `validation-matrix.xlsx`, `requirement-traceability.xlsx` |

## Inspect the repository first
1. `git status` / `git log --oneline -10`; note which features changed since the last test run (`PROGRESS.md`).
2. Find every existing test and how it runs: `backend/src/test/java` (`./mvnw test`), `tests/backend`, `tests/integration` (pytest, `.venv`), frontend component tests (`npm test` if configured), Playwright specs, CI workflow steps in `.github/workflows/`.
3. Read existing test data in `tests/test-data/` and seed scripts; reuse them.
4. Open the three workbooks and note sheet names, columns, dropdown values and existing IDs. Continue ID sequences; preserve formulas and formatting.
5. Never delete, skip (`@Disabled`, `pytest.mark.skip`, `.only`) or loosen an existing test to make a run pass. If a test is wrong, report it and get approval to change it.

## Step-by-step execution
1. **Scope**: list the requirement IDs and acceptance criteria under test.
2. **Derive scenarios** for each criterion: positive; negative (missing/invalid fields, wrong role, wrong state); boundary (just below / at / above every limit and threshold — e.g. 500 INR receipt rule, 1,500/day meals, 2,000/trip cab, 4,000/6,000 per night hotel by city tier, 25,000 and 1,00,000 claim totals); edge (zero, negative, very large amounts, weekend dates, duplicate by vendor/amount/date, by receipt hash, by date + receipt number, claimant with no manager, finance head's own claim, expired delegation, resubmission after send-back, sampled claim held from payout).
3. **Assign IDs** `TC-FE-###`, `TC-BE-###`, `TC-INT-###`, `TC-E2E-###`, linked to requirement and API IDs.
4. **Choose the level** for each: JUnit 5 (rules/engines), pytest API (contract, status codes, authorization, state transitions), pytest integration (multi-step flows through API + DB), component tests (forms/states), Playwright E2E (journeys). At least **10 written E2E cases** (source requirement).
5. **Test data**: synthetic only, in `tests/test-data/` or generated by seed with a fixed random seed. No real names, accounts or receipts.
6. **Security and validation review**: check each CLAUDE.md §5 bypass (B-01…B-12) with a test where possible; check OWASP-style issues — injection, XSS, CSRF (if cookie auth), IDOR (read/modify another user's claim), mass assignment, upload type/size bypass, CSV formula injection, secrets in repo (`git grep -i "password\|secret\|api[_-]key"`), dependency vulnerabilities (Maven dependency check, `npm audit`). Record each finding as real or false alarm with the reason in `architecture/security-review.md`.
7. **Execute** suites in order: backend unit → API → integration → frontend component → E2E. Capture command, date, totals, failures.
8. **Defects**: for each real failure add `BUG-###` to the `Defects` sheet with steps, expected, actual, severity, linked TC and requirement.
9. **Workbooks**:
   - `test-cases.xlsx` → `Test Cases` sheet (status Pass/Fail/Blocked/Not Run, executed by/on, defect ID) and `Defects` sheet;
   - `validation-matrix.xlsx` → one row per requirement with test IDs, totals, passed/failed, evidence, validation status;
   - `requirement-traceability.xlsx` → "Test Case ID(s)" and "Status" columns.
   Edit with openpyxl, preserving formats and formulas; recalculate if you add formulas.
10. **Report** in `PROGRESS.md` and the chat: commands run, pass/fail counts per suite, Must-have requirements not yet validated, open Critical/High defects, security findings.

## Expected outputs
- Automated tests in their correct locations
- Updated `deliverables/test-cases.xlsx` (cases + defects), `validation-matrix.xlsx`, RTM
- `architecture/security-review.md` findings
- Test report section in `PROGRESS.md`

## Quality checklist
- [ ] Every acceptance criterion has at least one positive and one negative test
- [ ] Every documented boundary tested on both sides and at the value
- [ ] Every bypass B-01…B-12 checked
- [ ] ≥ 10 written E2E cases covering the demo journeys
- [ ] All results come from runs executed in this session or CI, with commands recorded
- [ ] No test removed, skipped or weakened
- [ ] Workbooks consistent with each other and with the code; IDs continuous
- [ ] Every failure has a BUG-### or an explanation

## Rules for avoiding assumptions
- Expected results come from requirements, CL decisions and the contract — not from what the code currently does. If the code and the requirement disagree, that is a defect or a question, not a new expected result.
- If the expected behaviour is undocumented, mark the case *Blocked — Q-##* instead of guessing.
- Never mark Pass without execution evidence. "Should pass" is Not Run.
- Do not classify a security finding as a false alarm without stating the reason and the control that prevents it.
